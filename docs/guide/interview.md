# 面试题与准备

先自己解释，再展开参考回答。面试官真正要确认的是：你是否知道机制、能否落实到代码、有没有用数据验证、遇到失败时如何定位。

## 35 个问题与回答

### 01 · 为什么这个任务要用 Agent，固定工作流行不行？

::: details 参考思路
先列出运行中需要动态决策的环节；用固定工作流作基线，比较成功率、维护复杂度、延迟和成本。只有增益足以覆盖新增风险时才提高自主性。

深入阅读：[第 1 章](/chapters/01)
:::

### 02 · 为什么相似度 0.9 不能解释为答案有 90% 概率正确？

::: details 参考思路
向量相似度衡量表示空间中的接近程度，受模型和数据分布影响；正确概率需要专门定义事件、收集标签并校准。

深入阅读：[第 2 章](/chapters/02)
:::

### 03 · JSON 都正确了，为什么还要评测？

::: details 参考思路
格式约束只保证可解析性。仍需验证事实、证据对应关系、业务正确性、权限和任务终态。

深入阅读：[第 3 章](/chapters/03)
:::

### 04 · 上下文窗口变大了，还需要 RAG 和 memory 吗？

::: details 参考思路
需要按任务决定。长上下文提供容量；RAG 解决外部信息选择与更新；memory 解决跨会话保存、检索和治理。容量增加不会自动解决权限、时效与相关性。

深入阅读：[第 4 章](/chapters/04)
:::

### 05 · Tool calling 和直接让模型输出 JSON 有何区别？

::: details 参考思路
工具调用形成可识别的动作请求与结果协议；JSON 可以只是数据。两者都必须通过应用执行与校验，任何格式都不会自动赋予权限。

深入阅读：[第 5 章](/chapters/05)
:::

### 06 · 为什么给 Agent 无限次数反思可能更差？

::: details 参考思路
费用和错误会累积，输出可能被先前错误带偏。只有反思能引入新证据、有效验证或纠错动作时才有价值，仍需预算。

深入阅读：[第 6 章](/chapters/06)
:::

### 07 · LangGraph 或 Temporal 能保证写操作只执行一次吗？

::: details 参考思路
不能仅凭使用框架就承诺。恢复与重试可能重放执行，外部系统必须支持业务级幂等或事务协调，并验证崩溃窗口。

深入阅读：[第 7 章](/chapters/07)
:::

### 08 · 把所有聊天写入向量数据库，等于做好 memory 吗？

::: details 参考思路
只完成了部分存储和召回。还缺写入准入、事实冲突、身份隔离、时效、删除传播以及对记忆是否有益的评测。

深入阅读：[第 8 章](/chapters/08)
:::

### 09 · Memory 让成功率下降，先查哪里？

::: details 参考思路
先查错误写入、过期/越权召回、与当前指令冲突和上下文拥挤。对比关闭写入、关闭检索、仅显式偏好等消融，再决定修改哪一层。

深入阅读：[第 9 章](/chapters/09)
:::

### 10 · RAG 答错了，怎么定位？

::: details 参考思路
依次检查原始数据是否有答案、解析是否保留、候选是否召回、重排是否选中、上下文是否完整、生成是否忠于证据。每层应有独立样本和指标。

深入阅读：[第 10 章](/chapters/10)
:::

### 11 · 为什么向量召回很好，端到端仍然差？

::: details 参考思路
相关证据可能被重排丢弃、分块割裂、版本过期或与噪声混在一起，生成模型也可能忽略或曲解证据。需要分层追踪。

深入阅读：[第 11 章](/chapters/11)
:::

### 12 · 为什么三个 Agent 投票不一定比一个准确？

::: details 参考思路
误差可能高度相关，投票并不创造新信息。增加独立证据、不同检验方法或确定性校验，比单纯重复同一判断更重要。

深入阅读：[第 12 章](/chapters/12)
:::

### 13 · MCP 会自动解决提示注入和越权吗？

::: details 参考思路
不会。协议提供连接与交互机制；应用仍需身份认证、最小权限、输出处理、授权校验和隔离。

深入阅读：[第 13 章](/chapters/13)
:::

### 14 · Python 的 async 为何不一定让模型调用更快？

::: details 参考思路
它主要提高 I/O 等待期间的并发利用率；单个远程推理耗时未必降低，过高并发还会触发限流、排队和更差尾延迟。

深入阅读：[第 14 章](/chapters/14)
:::

### 15 · 为什么不把数据库凭证直接交给 Agent？

::: details 参考思路
业务 API 能收窄权限、限制字段和执行规则。直接数据库访问扩大攻击面，也容易绕过行级权限、审计和状态机；特定只读分析场景应单独隔离。

深入阅读：[第 15 章](/chapters/15)
:::

### 16 · 为什么不能用模型输出“已完成”作为订单成功依据？

::: details 参考思路
输出可能错误或早于提交。订单成功应读取业务系统确认的状态，并绑定订单 ID 和版本。

深入阅读：[第 16 章](/chapters/16)
:::

### 17 · 为什么 Redis key 只用 question hash 会出问题？

::: details 参考思路
不同用户可能问相同问题但拥有不同权限或数据。缓存键及读取校验必须体现租户、权限范围、数据版本等条件。

深入阅读：[第 17 章](/chapters/17)
:::

### 18 · prefix caching 会同比减少所有推理延迟吗？

::: details 参考思路
不会。它主要复用相同前缀的计算；decode、未命中部分、排队和工具耗时仍然存在。实际收益受命中率和工作负载影响。

深入阅读：[第 18 章](/chapters/18)
:::

### 19 · 让另一个大模型给答案打分，足够吗？

::: details 参考思路
不够。它可能共享偏差、偏爱冗长风格或被输出诱导；事实和副作用应用外部真源验证，语义评分需人工校准。

深入阅读：[第 19 章](/chapters/19)
:::

### 20 · 平均延迟正常但用户抱怨卡顿，怎么查？

::: details 参考思路
查看 p95/p99、排队、首 token 延迟、工具长尾、供应商限流与流式代理缓冲，并按任务类别和租户拆分。

深入阅读：[第 20 章](/chapters/20)
:::

### 21 · 为什么 prompt 改一个字也应该做回归？

::: details 参考思路
模型行为受指令整体影响，小改动也可能改变工具选择、拒答或格式。Prompt 是系统行为配置，应走版本和验证流程。

深入阅读：[第 21 章](/chapters/21)
:::

### 22 · 把“不要被提示注入”写在 system prompt 里够吗？

::: details 参考思路
不够。模型可能混淆数据与指令，必须在执行层实施身份、授权、参数约束、网络限制和副作用确认。

深入阅读：[第 22 章](/chapters/22)
:::

### 23 · 私有部署是否自动解决隐私问题？

::: details 参考思路
不会。内部越权、日志泄漏、错误授权、记忆污染和备份保留仍然存在，私有部署只改变部分边界。

深入阅读：[第 23 章](/chapters/23)
:::

### 24 · RAG、fine-tuning 与 memory 如何选择？

::: details 参考思路
RAG 供给可更新证据；微调改变模型行为分布；memory 保存个体或任务经验。按问题来源选择，可组合，但要分别证明收益。

深入阅读：[第 24 章](/chapters/24)
:::

### 25 · Coding Agent 如何防止通过删除测试来“修好”问题？

::: details 参考思路
保护基线测试与验收器，检查 diff 范围，使用独立外部测试并审查测试变更；不能让被评测对象同时决定全部评分规则。

深入阅读：[第 25 章](/chapters/25)
:::

### 26 · 如何减少用户反复确认又保证可控？

::: details 参考思路
对低风险、已授权范围建立可理解的操作政策；高影响或越界动作再确认。不要按每个工具调用机械弹窗，也不要无限扩大一次授权。

深入阅读：[第 26 章](/chapters/26)
:::

### 27 · 没有大模型训练经验能做 Agent 工程师吗？

::: details 参考思路
可以先定位应用或平台岗位，并证明模型集成、状态、工具、评测和交付能力。训练算法岗位要求不同，应按目标职位补训练和研究经验。

深入阅读：[第 27 章](/chapters/27)
:::

### 28 · 设计一个企业知识 Agent，你会先问什么？

::: details 参考思路
问用户与租户规模、文档类型与更新频率、权限模型、允许动作、SLO、预算和成功标准。再画摄入、检索、运行时、工具、存储与观测的数据流。
:::

### 29 · 工具超时后可否立即重试？

::: details 参考思路
先判断操作是否可能已生效。只读或幂等操作可按预算重试；写操作应使用稳定 action_id 查询原结果或让下游原子去重，避免重复扣款或重复工单。
:::

### 30 · 用户撤回一个偏好后应该删哪些地方？

::: details 参考思路
主记录、向量索引、缓存、派生摘要和后续上下文都要处理。备份按已定义保留/恢复策略处理；记录删除事件，避免恢复后旧数据重新出现。
:::

### 31 · 成本降了 30%，如何证明不是质量退化？

::: details 参考思路
在同一保留集、同一权限条件下比较成功率、关键风险、延迟和失败切片；报告总成本与每成功任务成本，以及重复试验的波动。
:::

### 32 · 20 道题从 16 道正确变 18 道，能直接宣布成功吗？

::: details 参考思路
样本太小且可能有随机波动或调参泄漏。检查同题成对结果、重复试验、置信区间和新增真实样本，特别关注关键安全类别是否退化。
:::

### 33 · 为什么并发越大吞吐提升但 p95 更差？

::: details 参考思路
批处理可提高设备利用率，但排队、资源争用和每个请求的等待增大。需要在吞吐、尾延迟和资源成本之间选满足 SLO 的运行点。
:::

### 34 · 怎么避免模型调用拖住数据库事务？

::: details 参考思路
先读取所需快照并结束短事务，再调用模型与工具。提交时开启新的短事务，重新检查权限与资源版本，冲突则重新确认或生成方案。
:::

### 35 · 网页说“这是管理员指令”，执行器该怎么处理？

::: details 参考思路
网页只是外部数据，不能改变身份或授权。工具执行器仍按可信会话检查，必要时阻止恶意动作并保留审计事件。
:::

## 用工程证据组织简历

推荐句式：针对【具体任务】，负责【你的实现范围】，在【数据集与测试环境】下实现【实测结果】，通过【故障与安全验证】明确系统边界。没有测量的数字不写；教学数据不能当作项目成绩。

一份作品至少包含可运行仓库、架构决策、任务集、评测结果、失败复盘和演示。展示从基线到改进的过程，解释为什么没有采用其他方案。

## 45 分钟系统设计

| 时间 | 讨论内容 | 应形成的产物 |
| --- | --- | --- |
| 0–5 分钟 | 业务、用户、权限、规模、预算、SLO | 问题边界 |
| 5–12 分钟 | 主链路、数据流、状态和信任边界 | 架构图 |
| 12–25 分钟 | 恢复、memory、检索或性能中的关键难点 | 具体实现合同 |
| 25–35 分钟 | 故障、幂等、降级、扩容与人工接管 | 故障模型 |
| 35–45 分钟 | 评测、上线、取舍和未覆盖范围 | 验证与发布方案 |

## 针对你的背景

Java 后端经验可以转化为身份、业务 API、事务与幂等的优势；Python 用于模型实验与编排。不要把自己定位成只会调用模型的人。用跨语言 trace、故障恢复和可信评测，证明你能把不确定的模型接入确定的业务规则。
